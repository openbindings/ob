1. **Blocking — edit refusals violate the exit-status contract.** `ob merge d other` says “refused…nothing was written” but exits **1**. Referenced-operation removal, alias-based rename refusals, and edits rejected for introducing non-conformance also exit 1. Scripts cannot rely on the promised distinction between failure and refusal. Return **3** for these cases, preserving 1 for failures and negative checks.

2. **Blocking — `invoke --no-check` contradicts the invocation interface.** `ob invoke d createTask --binding createTask.http --input '{"title":5}' --no-check --frames` completes successfully. The operation-invoker contract requires input/output validation; optional validation in core OpenBindings does not waive this interface’s requirements. Remove `--no-check` from this surface.

3. **Major — `source pull` lacks a conflict policy for shared operation contracts.** Its help promises to update operation schemas from sources, and the sample changes `listTasks.output`. After an author edits that contract—or two sources propose different schemas for an operation—nothing specifies whose definition wins. Document-rule validation cannot establish that all bindings still realize the changed contract. Refuse conflicting proposals and provide explicit resolution, with changes shown per operation and source.

4. **Major — `mcp` has no documented binding-choice path.** `ob mcp d --operation createTask` advertises a tool for an operation with two invocable bindings, while invocation requires an explicit choice. The command offers only operation filtering; neither its help nor its options explains how the caller makes that choice. Add explicit binding selection to server configuration or the exposed invocation interface, and diagnose unresolved choices clearly.

5. **Major — delegate registration requires different operations from the supplied interface.** `ob delegate roles -F json` requires `openbindings.binding-invoker.listSupportedKinds` and `checkKindSupport`; the binding-invoker document specifies `listBindingSpecs` and `checkBindingSpecs`. A delegate implementing that interface would not meet the advertised registration requirements. Align the exact operation identifiers, retaining the distinction between advisory listing and authoritative support checking. This is separate from the excluded “role” terminology issue.

6. **Major — context accepts values the interface cannot carry.** `ob context set S --value '[]'` succeeds, as does `ob invoke d completeTask --context '[]' --input '{"id":"x"}'`; `null` also succeeds. The binding interface carries an opaque **object**, not arbitrary JSON. Require objects at both entry points and reject other types with exit 2 before replacing context or invoking.

7. **Major — `patch` promises an unnecessarily strict repair barrier.** Its help requires the result to be conformant. A document with two independent violations therefore cannot receive a patch repairing just one, even though incremental repair is a normal authoring job. Apply the common policy of refusing newly broken rules while permitting repairs that leave existing violations, and explain remaining violations separately.

8. **Major — `start` combines serving with implicit trust installation.** Its help says the first run installs a local certificate authority. A user starting an OBI service thereby also requests a machine trust change, with no separate setup choice. Make CA installation explicit and independently actionable; ordinary startup should use an already configured certificate or a documented local HTTP mode.

9. **Minor — `init` breaks the agreed creation syntax.** `ob init -o d` exits 2 because `-o` is unknown, whereas other creation commands use `-o, --out`. Adopt `init -o <obi>` and keep omitted output as stdout. Update root examples accordingly.

10. **Minor — preflight accepts incompatible invocation options silently.** `ob invoke d createTask --binding createTask.mcp --preflight --frames` exits 0 but prints a bare requirements object, not frames. Adding `--input` silently ignores that input. Make preflight’s distinct output contract explicit and reject invocation-only options with exit 2.

11. **Minor — `mcp` silently accepts an unknown operation filter.** `ob mcp d --operation missing` exits 0 and reports “Serving 0 tools.” A typo becomes an apparently successful but useless server setup. Resolve every explicitly requested name, reject unknown names, and diagnose explicitly selected operations that cannot be exposed.

12. **Minor — completion is advertised but unreachable.** Root help lists `completion`, yet both `ob completion --help` and `ob completion zsh` report an unknown command and exit 2. Make the advertised command reachable.

13. **Minor — `compat` names an inaccessible comparison policy.** Help invokes “profile OB-2020-12,” but provides no explanation or documentation route; its JSON report omits that policy identifier. For `ob compat implementation contract`, users cannot establish the policy governing absent schemas, unsupported constructs, or reference availability. Publish the profile, link it from help, and include its identifier in structured reports.

The findings above distinguish observed responses from help-level design gaps. I have not counted fixed sample documents, placeholder results, or nonpersistent edits as defects.
