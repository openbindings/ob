1. **Blocking — schema-edit guards confuse conformance with schema execution.**  
   `ob schema add tasks.obi.json Another --value '{"$ref":"https://unavailable.example/schema.json"}'` exits **3**, alleging an OBI-D-10 violation because the resource is unavailable. Likewise, `ob operation add tasks.obi.json x --input-schema '{"type":"string","pattern":"(?<=x)y"}'` rejects a valid ECMA-262 pattern using another regex dialect’s error. Neither establishes document non-conformance: OBI-D-10 checks the pinned meta-schemas without resolving document references, and §5.2 separates evaluation limitations from document rules. **Change:** separate document validation from compilation for runtime use; accept these edits, and report resolution or evaluation limitations only when relevant.

2. **Blocking — reference checking does not follow the document’s schema model.**  
   With `ob schema add tasks.obi.json Another --value …`, all these valid schemas exit **3**:
   - `{"$ref":"#/operations/createTask/input"}`: the checker searches a synthetic meta-schema root.
   - `{"$ref":"#/%73chemas/Task"}`: the checker fails to percent-decode the fragment.
   - `{"const":{"$ref":"no-such"}}`: literal instance data is mistaken for a schema reference.

   These violate distinct requirements of §7: all OBI positions are addressable, fragments are decoded, and schema traversal excludes instance data. **Change:** implement the specified schema-position traversal and resource boundaries, resolve document pointers against the OBI, and leave values under `const`, `enum`, and `examples` uninterpreted.

3. **Major — `compat` documents the wrong aggregate verdict precedence.**  
   For `ob compat new.obi.json old.obi.json`, consider one missing operation plus another comparison made indeterminate by differing `pattern` constraints. Help promises exit **1**, reserving **4** for cases where nothing is known incompatible. OB-2020-12 instead specifies **indeterminate > incompatible > compatible**. **Change:** retain both individual findings, but report an indeterminate aggregate and exit 4; align help and JSON vocabulary with that rule.

4. **Major — token-provider binding selection is underspecified across operations.**  
   `ob context set https://api.example.com --token-provider https://auth.example.com --token-binding mint.http --token-binding refresh.http` accepts one ordered list. Help says selection works like `invoke`, whose strict rule rejects a list containing another operation’s binding; mint and refresh necessarily have different binding keys. The documented surface therefore cannot unambiguously express both choices. **Change:** define operation-specific selection, either by grouping keys by their owning operation as `mcp` does, or by accepting an explicit operation-to-binding mapping. Explain how that policy applies during renewal.

5. **Major — secret input handling has inconsistent escape routes.**  
   `ob context set https://api.example.com --header 'Authorization=Bearer abc'` succeeds, although the ruling says secrets never go on the command line. Conversely, `--config password=@secret.json` has no documented file-input meaning: configuration accepts JSON or a bare string, unlike headers. A safe configuration update therefore requires replacing the entire context through `--value`. **Change:** reject literal values for recognized credential-bearing headers and provide explicit file/stdin input for individual configuration points, preserving unrelated stored fields.

6. **Major — `source pull` cannot name a second binding for an existing operation/source pair.**  
   `ob source pull tasks.obi.json httpApi --target 'POST /tasks/{id}/archive' --operation completeTask` exits **3** because its generated name, `completeTask.http`, already exists. Refusing an overwrite is correct, but the command offers no way to choose another name, despite the model allowing multiple bindings through the same source. **Change:** add a binding-name option and an actionable collision diagnostic. Authors should not have to abandon source-assisted binding creation and reconstruct opaque content manually.

7. **Minor — value-validation JSON changes shape with input transport.**  
   `ob validate tasks.obi.json --operation createTask --input '{"title":"x"}' -F json` returns top-level `fits` and `problems`. Supplying the same single value through `--input -` returns `results: [...]`; repeating the flag changes it again to that array form. A script switching input delivery must also change its parser. **Change:** always return an indexed `results` array with consistent per-result fields.

8. **Minor — identity renames violate the stated no-change convention.**  
   `ob operation rename tasks.obi.json createTask createTask` exits **3**, as do corresponding binding and schema renames, claiming the destination already exists. The root exit contract says an edit already true is “no change,” exit **0**. **Change:** recognize identical source and destination before checking destination collisions.
